# 多模型聊天室

本机网页工具：**输入一个问题 → 多个模型在同一份公共消息池里轮流发言、互相质疑 → 最后输出带「共识 / 分歧 / 结论」的纪要。**

**主持人是你本人，不是模型。** 模型只负责发言，什么时候结束由你决定。

设计与需求见 `BRIEF.md`；实测探活记录见 `PROBE.md`；进度快照见 `PROGRESS.md`。

---

## 一、怎么启动、两个入口

双击 **`start.bat`**（浏览器会自动打开 http://127.0.0.1:8765/）。

命令行方式：

```
python run.py
```

- 换端口：`set PORT=9000 && python run.py`
- 不想自动开浏览器：`set NO_BROWSER=1 && python run.py`
- 停止：在那个窗口按 Ctrl+C

首次运行如果提示缺依赖，双击 **`install_deps.bat`** 装一次即可。
依赖只有三个：`fastapi`、`uvicorn[standard]`、`httpx`，装在隔离环境
`~/.workbuddy/binaries/python/envs/multiai`，不污染系统 Python。

### 两个入口，两种身份（2026-10-14 用户定）

| 入口 | 谁能进 | 能干什么 |
|---|---|---|
| **http://127.0.0.1:8765/** | 任何人（填个不重复的昵称就能进） | 聊天、建房间、管自己的房间。**看不到**模型库、**看不到**厂商 / API Key |
| **http://127.0.0.1:8765/admin** | 只认管理口令 | 改**全局模型库**、填**厂商 / API Key**、改**规则**、增删**角色库**、释放**昵称账号**、改**管理口令** |

- **管理口令默认是 `Qq!15732382019`** —— 第一次进 `/admin` 用它登录，**进去后建议在「管理口令」区块改掉**。
  改口令会让**所有已经登录的 /admin 页面立刻失效**（要重新登录），这是有意做的（改口令 = 踢下线）。
- 口令不是明文存的：`config.json` 的 `admin` 段里只有 **PBKDF2-SHA256 哈希 + 随机盐**。
  要改口令请在 `/admin` 页面里改，**别手改 config.json**（手改会被当成"没改过"，服务一启动就补回默认值）。
- **普通用户的昵称就是账号：不用密码，跨浏览器认人** —— 同一个昵称在任何浏览器 / 设备进来都是同一个人
  （2026-10-15 改；详见下面《进门：昵称就是账号》与《右上角：登录 / 退出》两节）。
- **默认讨论室没有房主**：所有进去的人权限完全一样（等于过去的「房主」全权），而且它**不能被删除**
  （详见下面《默认讨论室：无主房间》一节）。

> ⚠️ 这个「分权」是**页面级 + 接口级**的：服务端对所有改全局配置的写接口都要求 `X-Admin-Token`，
> 普通用户就算手打接口也是 401。
>
> **公网发布（2026-10-15 起支持）**：本机自用仍只监听 `127.0.0.1`；发布到公网时平台会注入 `PORT`
> 环境变量，`run.py` 一检测到 `PORT` 就自动改成监听 `0.0.0.0`、并关掉自动开浏览器。
> 发布用的是一份**脱敏副本**（真实 API Key 已清空、不带本机历史），见《七、发布到公网》。
> 注意它仍然**没有 HTTPS**，而且默认管理口令等于公开 —— 上线后第一件事就是去 `/admin` 改口令。

## 二、界面怎么用

三栏：**左 = 房间列表 + 规则/角色说明 / 中 = 消息流 + 常驻主持人控制条 / 右 = 本房间参与者**。

**左栏底部两个说明模块（规则 / 角色）** —— 只读，把「实际发给模型的提示词」摊开给你看：
「规则」逐条列出共享规则（`config.json → shared_prompt`，每个模型每轮都带）；
「角色」按分组列出预置角色的提示词原文（选中后它才会进 system）。
两个模块和右栏一样可点标题栏折叠。**内容只有管理员能在 `/admin` 里改**，这里就是给你看的。

**右栏只有一个区块「本房间参与者」**，可点标题栏折叠，折叠状态记在浏览器本地，刷新后保持。
标题栏里的「添加模型 / 管理成员」按钮照常点击，不会触发折叠。

> 2026-10-14 之前，右栏还有「模型库」和「厂商 / API Key」两个区块 —— 现在它们**搬到了 `/admin`**，
> 首页不再有任何能改动全局模型库的入口。


### 外观主题：青瓷雅致（2026-10-15 第九批）

界面配色 = **浅青灰 + 青瓷绿（主色）+ 木色（真人 / 房主）**。改动全在 `static/style.css` 一个文件里，
**没有一行 JS / HTML / 后端改动**（用户要求「只美化外观，不动功能代码」，布局尺寸也一律没动）。

- **模型名彩色圆点**：聊天区每条模型发言的昵称前、以及右栏「本房间参与者」卡片名前的圆点，
  按 **青瓷 → 琥珀 → 黛蓝 → 紫檀 → 松绿** 五色轮转。轮转是**按出现顺序**的视觉多样性，不是「按模型固定配色」
  （CSS 拿不到模型 id，也不值得为它改 JS）。**真人发言的圆点是木色**，一眼区分人和模型。
- **自动跟随系统深浅色**：`@media (prefers-color-scheme: dark)` 里**只覆盖 `:root` 的 CSS 变量**，
  其余样式通过 `var()` 自动换色 —— **不需要 JS，也没有手动开关**。系统切到深色，页面跟着变。
- **正文放大一档**：正文字号 13 → 13.5px、行高 1.6 → 1.75。
- **hover 轻微过渡**：按钮 / 卡片 / 房间项等统一 0.18s 过渡（**只过渡颜色类属性**，不带宽高位置）；
  系统开了「减少动态效果」会自动全部关掉。

> ⚠️ **维护须知**：新增样式请**用 CSS 变量取色**（`var(--accent)`、`var(--panel-2)` …），别写死 `#fff` / `#f5f5f2`
> —— 写死颜色在深色模式下会瞎。所有颜色都在 `style.css` 顶部的 `:root` 里，**深浅两套变量并排**。

### 发言调度：你说一句 = 一轮，参与者轮流发言（2026-10-13 定稿）

控制条最左边的 **「自动轮流」开关**（默认开）决定发一条消息之后谁开口：

- **开**：在输入框发一句话 → 这一轮房间里**每位参与者依次各发言一次**，不用手动点。
  轮次号 = 你发过几句话（历史里显示「第 N 轮」）。发消息时 `@模型名` → 他排本轮第一位，其余人照旧依次发言。
- **关**：发消息只入池，等你在右侧点名。

**轮内间隔（默认 3 秒）**：上一位说完，不会立刻接话，先等 **间隔** 秒再请下一位开口
（控制条上的「间隔 / 秒」输入框，范围 **0.5~60 秒**、支持 0.5 秒小数，是**房间级设置**，
写回 `data/room_index.json`）。等待期间控制条会显示 `⏳ 等 X.X 秒后轮到「某某」`——
这段空档就是留给你**打断或点名**的窗口。一次性只提交一位发言（点名、指定总结）时不插间隔。
下限 0.5 秒（2026-10-15 第十二批由 3 秒放宽）：填 0 或负数会按 0.5 秒走。**关掉思考后每位只要 1~3 秒，
3 秒空档就显得很浪费**，所以允许调到 0.5~1 秒。

**发言顺序从哪来**：就是右栏「本房间参与者」列表**从上到下的顺序** ——
存储上是房间文件里 `rooms[].participants` 数组的排列顺序（2026-10-15 起该文件是
`data/room_index.json`，此前是 `config.json`），**不是**按模型名、厂商或能力排序，
每轮都一样（同一套顺序，第一个人恒定先开口）。`@模型名` 只把被点的那位**挪到本轮第一位**，
其余人的相对顺序不变。想改顺序 = 改 `participants` 数组的顺序（改完全局重载即可生效）。

> ⚠️ 一次发言 = 一次计费调用（连同完整历史重发）。默认房间 7 位参与者，**一条消息就是 7 次调用**，
> 跑得快也烧得快——成本护栏 `cost_guard.max_total_calls` 只做保险丝。

### 觉得回答太慢？先调这两处（2026-10-15 第十二批）

有用户反馈「模型回答比网页版慢很多」。**实测定位到两个真正的大头，都在页面上能调**（不是网络慢、
不是 `max_tokens` 给小了、也不是上下文太长）。同一个问题、串行跑，逐项对比：

| 模型 | 原样 | 关掉思考 | 关思考 + 限长 200 字 |
|---|---|---|---|
| 豆包 `doubao-seed-2-1-pro` | **148.6 秒**（思考 907 字 + 正文 2408 字） | 29.7 秒 | **3.6 秒** |
| 千问 `qwen3.8-flash` | 51.3 秒（思考 162 / 正文 3028） | 19.2 秒 | **1.7 秒** |
| DeepSeek `deepseek-v4.1-flash` | 37.2 秒（思考 3458 / 正文 950） | 11.7 秒 | **2.6 秒** |
| 智谱 `glm-4.7-flash` | 63.0 秒（思考 2040 / 正文 1408） | ⚠️ 429（**这家关不掉**） | 35.7 秒 |

两个大头：**① 模型"思考"（`reasoning_content`）占了首字时间的大半；② 正文不限长时它会写到两三千字。**
默认房间 3 位参与者 + 2×3 秒间隔 ≈ **244 秒/轮**；关掉思考 + 限长 200 字后 ≈ **14 秒/轮**。

**① 关掉思考 —— 在 `/admin` 的模型库里改**：模型编辑弹窗的「思考档位」下拉现在有 **`off`** 一项
（选它＝彻底关掉思考，回答最快）。点开时下面会显示**这一家到底关不关得掉**：

| 模型 | `off` 实际发什么 | 能不能关 |
|---|---|---|
| 方舟 `doubao-seed-*` | `thinking.type = disabled` | ✅ 实测（思考 1118→0，156.6s→7.5s） |
| 百炼 `qwen*` / `deepseek-v4.1-flash` | `enable_thinking = false` | ✅ 实测（42→0 / 180→0） |
| 腾讯 `hy*` / `kimi-k3` | `thinking.type = disabled` | ✅ 实测（208→0 / 256→0） |
| 腾讯 `minimax-m3` | `thinking.type = disabled` | ⚪ 能关但没用（自适应思考，本来就不思考） |
| 智谱 `glm-4.5` / `glm-4.7` | `thinking.type = disabled`（或 `enable_thinking`） | ✅ 实测（思考归零） |
| 智谱 / 百炼 `glm-5.3` | —— | ❌ **关不掉**（官方回 400「该模型始终思考」）→ 什么都不发 |
| DeepSeek 官方 | `thinking.type = disabled` | 📄 文档支持，本机未实测（Key 余额 402 拦在最前） |

> ⚠️ **关不关得掉是「按模型」判的，不是「按厂商」**：同一家网关里挂着别家的模型是常态，
> 所以腾讯的 DeepSeek 关得掉、腾讯的 `glm-5.3` 关不掉。界面上的角标和说明是实时算的。
> ⚠️ **风险家族**：族里出过「关不掉」型号的家族（智谱 GLM / 腾讯 Kimi / 百炼·官方 DeepSeek），
> 同族**新型号默认不自动关**（怕又撞上强制思考型号被回 400），只有点名核对过的型号才照发。
> 新加的模型确认能关，就在「off 关法」里手动指定。
> 🧪 **加模型前先敲一下这条**（不耗额度）：`python tools/_check_off_plan.py --model zhipu:glm-5.4`

> 界面上「思考档位」还有 `low / high / max`（＝把思考**压小**，不保证关闭）；`off` 是唯一能**彻底关**的档。
> 免费线路的思考量本身会抖动，档位是「倾向」不是「保证」。

**② 缩短正文 —— 在 `/admin` 的模型库把 `max_tokens` 调小**（每个模型一个值，比如 300~800）。
另外房间的 `shared_prompt` 里若写了「把理由说完整」之类的字样会鼓励长回答；要短就把它去掉。

**③ 间隔也可以调小 —— 控制条上的「间隔 / 秒」**，2026-10-15 起下限从 3 秒放宽到 **0.5 秒**
（关掉思考后每位只要 1~3 秒，3 秒空档很浪费）。

**④ 优先挑快模型**：同是免费模型，实测 `qwen3.8-flash` / `deepseek-v4.1-flash` 比 `doubao-seed-2-1-pro`
快一个数量级；`glm-*` 免费线还有 429 限流重试的额外等待（退避会让人以为「卡住了」）。

> ⚠️ **别把慢都归给 `max_tokens`**：实测把 `max_tokens` 从 8000 降到 600 时输出长度几乎没变——
> 因为自由讨论的提示词本身就鼓励长回答。真正让首字变快的是「关思考」，让总时长变短的是「关思考 + 限长」。

### 某个模型调用失败 → 跳过它，下一位继续（2026-10-15 第十批）

以前某位模型调用失败（典型是 429 限流），**整轮当场报废**：界面上连弹两条红提示
（`调用失败：HTTP 429…` + `ProviderError(...)`），排在后面的模型全部没机会开口。

现在的行为：

- 失败的那位会弹一条 **「「某某」调用失败，已跳过、由下一位继续：…」**，然后**轮到下一位**，整轮照常跑完。
- 失败的模型**不会有半截内容写进历史**（跟打断的处理一致）。
- 如果一轮里**所有**模型都失败（且不止一位），会额外汇总提示一条
  「本轮 N 位模型全部调用失败…已全部跳过」。
- **成本护栏（全局调用上限）达到时仍然整轮立刻停** —— 这是保险丝，不属于「跳过」范畴。
- 打断（停止 / 点名）的优先级不变：任何时候都能接管，半截输出照样丢弃。

> 💡 429 多为免费额度限流：跳过通常能靠下一位（往往在别的厂商）把话接上；
> 但若同一厂商的几位连续 429，这一轮里他们会一个个被跳过 —— 想让某位补说，等会儿再点名即可。

### 主持人的五种能力（BRIEF 第一节 ③ 的硬需求）

| 能力 | 怎么操作 |
|---|---|
| **点名发言** | 右侧某位参与者卡片上的「发言」按钮；或在输入框里 `@模型名 你怎么看`。**任何时候都优先**：点它会立刻打断本轮剩余安排，让这位马上接着说 |
| **指定总结** | 控制条右侧选「总结者」下拉 → 点「指定总结」。**任意模型都能当总结者，不固定在谁身上** |
| **自由发言** | 控制条填「自由讨论 N 轮」→ 点「开始」。跑完自动停 |
| **打断** | 控制条右侧「停止」。**立刻生效**：当前模型已吐出的半截内容按约定直接丢弃，不写进历史 |
| **定向回应** | 每条模型发言右下角悬停出现「让…回应这条」→ 选一个模型，它就针对那条发言作答 |

另外：`Ctrl+Enter` 发送；顶部「导出 Markdown」把整个房间导出成纪要文件；「清空」只清历史、保留房间配置。

### 进门：昵称就是账号，免密码（2026-10-15 改）

打开首页第一件事是填**昵称**，它同时就是你的账号：

- **不用密码、不用注册** —— 昵称就是身份。服务端把昵称映射到一个固定的 `uid`，
  所以**同一个昵称，换任何浏览器 / 设备 / 清了站点数据进来，都还是同一个人**。
- **昵称全局唯一**：别人已经占用的昵称，你填了就等于是"那个人"（见下面的风险提示）。
- 昵称是**署名**用的：房间里的真人名单、消息头、导出纪要都按它显示。
- 绕过 `/api/login` 直接连 WebSocket 也没用：服务端在 `resolve_join` 里按昵称解析出同一个 `uid`，
  以服务端解析结果为准，前端传什么都不算。
- **被移除过的昵称当场就自由了**（2026-10-15 第三批改定）：管理员在 `/admin → 用户库` 点「移除」
  就是**直接删掉**这个人 —— 不拉黑、不进任何名单。删完之后这个昵称谁都能用（含他本人），
  再填一次就是**重新登记**（拿一个全新 uid）。

> ⚠️ **免密码的代价（用户已知情接受）**：知道昵称的人可以顶着你的名字进来，**没有任何验证**。
> 这是"跨浏览器同一个人"这个需求下最简单可行的做法，适合**熟人小圈子**用。
> 要真正防冒名，得再加一层密码 / 验证码（目前**没做**）。

### 右上角：登录 / 退出聊天室（2026-10-15 新增）

顶栏右上角多了一个**用户区**（`.userbox`，左边一条竖分隔线）：

| 当前状态 | 显示什么 | 点它做什么 |
|---|---|---|
| 没登录 | **登录** 按钮（主色小按钮） | 弹出昵称门槛页，填昵称进房 |
| 已登录 | 昵称胶囊 + **退出** 按钮 | 「退出」清掉本机昵称 / uid / `myRooms`，回到门槛页 |

- 「退出」**只清身份，不动 API Key**：本机存的 `myKeys` 保留，重新登录后还在。
- 退出**不会**把人从任何房间的成员表里摘掉 —— 那要房主在房间「管理成员」里踢，
  或管理员在 `/admin → 用户库` 里全局移除。
- 门槛页上多了一个 **「先看看」** 按钮：不填昵称也能进去看界面，但**进不了房间**
  （点房间会被弹回门槛页，要求先登录）。

### 房间管理

左侧房间：**新建 / 重命名 / 删除 / 复制**。

- **新建的房间默认没有任何模型参与者**（2026-10-14 用户定）：进去后到右栏「本房间参与者」
  点「添加模型」自己挑 —— 不会再把模型库里全部已启用的模型一股脑塞进去
- 空房间里的参与者面板会写明「这个房间还没有模型参与者」，照着提示加就行；
  这时候发消息／点「启动新一轮」会明确报错提示（不会静默什么都不发生）
- 「复制」会把原房间的**参与者也一起复制**，只换一两个模型就建成新房间
  （`BRIEF.md` 里标记为最高频操作），想省事就用这个
- 每个房间有**独立的参与者名单、角色、轮次设置和对话历史**，互不串台
- 历史按房间分文件存 `data/rooms/<roomId>.json`

### 房间准入：公开房间 vs 房间号（2026-10-14）

房间分两种，由 `rooms[].open` 决定：

| 类型 | 怎么进 | 房间号 |
|---|---|---|
| **公开房间**（`open: true`） | 打开页面点一下房间名就进，不需要任何口令 | 没有（`code` 留空） |
| **私有房间**（`open: false`，默认） | 必须输入房主给的 **6 位房间号** | 建房时生成，只有房主能看 |

- **默认讨论室就是公开房间** —— 谁都可以直接用，不用问任何人口令。
- 房主在左栏点自己房间的「重命名」（弹窗标题现在是**房间设置**）→ 勾选/取消
  「公开房间（不要房间号，谁都能进）」即可来回切：
  改公开会**清空房间号**，改回私有会**自动补一个新的 6 位号**（否则谁都进不来、也没号可分享）。
- 房间卡上带「公开」标；房主在公开房间的顶栏看到的是「公开房间 · 谁都能进」，不是号码。
- 成员**不能**改这一项（「谁能进这个房间」属房主配置权，服务端 403）。
- ⚠️ 公开房间的「公开」是就**本机/局域网可达范围内**而言：别人得先能打开你这个地址
  （默认只听 `127.0.0.1`，要给别人用需要 `HOST=0.0.0.0` 且放行防火墙）。

### 默认讨论室：无主房间（2026-10-15 用户定）

用户原话：「默认讨论室还是有房主，应该取消。所有用户在默认聊天室的权限是一样的。」

- **字段**：`rooms[].no_owner`（bool）。`true` = **无主房间**：没有房主，**每位成员都是全权**
  （建/改/删房间配置、管理成员、触发模型轮、清空——过去只有房主能干的事，现在人人能干）。
  `false`/缺省 = 过去的老规矩（first-join 者认领房主，房主与成员分权）。
- **只有默认讨论室（`room-default`）是无主房间**，由 `_backfill_rooms()` 强制：
  把它设成 `no_owner: true` 并**清空残留的 `owner_key` / `owner_uid`**；其余房间一律 `no_owner: false`。
  这条是**幂等的**，服务每次 load 都会校正（否则老配置里认领过房主的默认房间会一直是房主）。
- **权限判定**：`main.py._is_owner_of()` 对无主房间**直接返回 `True`**；
  `_do_join()` 遇到无主房间**不发钥匙、不认领房主**（`owner_key=''`），`joined` 事件里回 `ownerless: true`；
  `_broadcast_members()` 对无主房间**不下发 `owner_uid`**（成员名单里不再有「房主」角标）。
- **不能删**：`DELETE /api/rooms/{id}` 对无主房间直接 **403**（"默认讨论室是所有人共用的房间，不能删除"）。
  界面上它的卡片**没有「删除」按钮**（保留「复制」「改名」），标签是「人人可管理」而不是「房主」。
- **前端**：`roomNoOwner(id)` / `iAmOwnerless()`；顶栏房主码位置对无主房间显示
  **「公开房间 · 人人可管理」**（不再是「房主」）；`renderRooms()` 据此隐藏删除按钮。
- ⚠️ **副本不是无主房间**：`duplicate_room()` 明确写 `no_owner: False`（复制时人是谁就是谁的，复制者 = 房主）。
- ⚠️ **自检里不要拿真的 `room-default` 做 WS join 权限测试**：它现在不会认领房主了，但仍是用户在用的房间；
  权限用例一律用自建房间。默认讨论室只做**只读断言**（`no_owner`/`owner_uid` 为空/不能删）。

### 回收站（删除的房间先到这里）

左栏「回收站」按钮（带条数角标）→ 弹窗里可以对每条做两件事：

| 操作 | 实际发生了什么 |
|---|---|
| **还原** | 房间配置回到房间文件（`data/room_index.json`），历史文件从 `data/trash/<条目>/history.json` **搬回** `data/rooms/<roomId>.json`，房间和之前的对话都原样回来 |
| **彻底删除** | 本机 Windows：整个条目目录交给 **Windows 回收站**（走系统 Shell API），你仍能在系统回收站里找回；**没有系统回收站的环境（公网 Linux 沙箱）：直接删掉**（见下） |

**回收站是按人分开的**（2026-10-15 用户要求）：「回收站中应该只能看到登录的用户自己删除的房间，
不能看到其他用户删除的房间。」—— 每个条目在删除时就记下 `deleted_by_uid`，
列表 / 还原 / 彻底删除都只看得到、也动得了**自己删的那些**。

| 谁在看 | 看得到什么 |
|---|---|
| 普通用户（`/`，带 `X-User-Uid`） | 自己删的条目 + **没有归属的老条目**（这条功能上线前删的，谁都看得见，否则会永远消失在界面上） |
| 未登录 / 匿名 | 只有无归属的老条目 |
| 管理员（`/admin`） | **全部条目**。管理员删的房间记 `deleted_by_uid='admin'`（真实用户拿不到的保留值）→ 不会串进任何普通用户的回收站 |

设计上的硬规则：

- **删除 = 移动，不是抹除**。点「删除房间」时，配置快照写进 `data/trash/<条目>/meta.json`，
  历史文件用 `os.replace` **移动**过去，全程可逆；这条对**任何环境**都成立。
- **「彻底删除」在本机 Windows 上仍然不硬删**：把目录交给系统回收站（`FOF_ALLOWUNDO`），
  **最终释放权在你手上**（跟这个工位其他项目的删除规则一致）。
- ⚠️ **没有系统回收站的环境里，「彻底删除」就是真删**（`shutil.rmtree`）。这是 2026-10-15 用户
  明确选的口径 —— 原来那种「不支持回收站 → 拒绝删除」的做法，让公网用户**永远清不掉回收站**
  （公网截图报的就是「当前环境不支持 Windows 回收站，已放弃删除」）。前端按钮文案会跟着环境变：
  有回收站说「交给 Windows 回收站」，没有就说「⚠️ 会真正删掉，无法找回」。

## 三、配置与 API Key

配置分两处放：**全局配置**在 `config.json`，**房间定义**在 `data/room_index.json`（2026-10-15 搬家，见第七节）。

```
config.json                         ← 全局配置（发布时会被本地那份整体覆盖）
  providers（厂商预设：base_url / 免费额度 / 已知坑）
     ↓ 被引用
  models（全局模型库 —— 页面上增删改的就是这里）
     ↓ 被引用 + 覆盖角色（存 role_presets 的 id）
  role_presets（角色预置库：13 个角色，分 4 组，每个带一句注入 system 的提示词）

data/room_index.json                ← 房间定义（发布时**不上传**，所以线上房间能活过重发布）
  rooms（房间：参与者名单 / 角色 / 轮次 / 房间号 / 房主钥匙 / 真人成员表 / 历史文件路径）
     ↑ 引用 models 的 id
```

**角色怎么设**：不再手填文本。下拉选一个预置角色（质疑者 / 提问者 / 补充者 / 落地派 / 用户代言人 …），
**只在房间参与者上设**（模型库不存角色，2026-10-13 定稿），不设就是真的没有角色。
角色名会出现在同伴看到的参与者名单里，完整提示词只注入该模型自己的 system（见 `PROMPTS.md`）。

**读写规则（写死的）**：页面上的任何增删改都走同一个模块 → 原子写 JSON → 内存热重载 → 通知前端刷新。
改全局配置写 `config.json`，改房间写 `data/room_index.json`（**`config.json` 里刻意不写 `rooms`**）。
手工改了这两个文件后，在 `/admin` →「厂商 / API Key」区点「重载」就能拾取（热重载同时盯两个文件的 mtime）。

**谁能改什么（2026-10-14 分权）**：

| 改动 | 在哪改 | 服务端怎么拦 |
|---|---|---|
| 模型库增删改、厂商 / API Key、规则、角色库、昵称账号、管理口令、**房间库（看全部房间）** | **只有 `/admin`**（带 `X-Admin-Token`） | `POST/PUT/DELETE` 这些接口全部 `_require_admin()`，无令牌一律 **401** |
| 房间（建房 / 改名 / 公开·私有 / 参与者 / 清空） | 首页 `/`，**房主** | `X-Owner-Keys` 头，非房主 **403** |
| 房间（**删除**） | 首页 `/` 房主，**或 `/admin` 房间库的管理员** | 房主钥匙 **或** 管理令牌，两者都没有 → **403** |
| 回收站（列表 / 还原 / 彻底删除 / 清空） | 首页 `/`，**条目归属人**（看 `X-User-Uid`） | 不是自己删的 → **403**；管理员不受限 |
| 同上（**默认讨论室例外**） | 首页 `/`，**房间内任何人** | 无主房间（`no_owner: true`）人人全权；仅「删除房间」被拦（403，管理员也拦） |
| 聊天 / 自动轮流 / 停止 / 启动新一轮 / 指定总结 | 首页 `/`，房间内任何人 | 房间成员校验 |

⚠️ **`X-User-Uid` 只用来过滤回收站的可见范围，不是权限凭据** —— 免密码身份下这个值伪造成本极低；
真正决定「能不能动」的仍然是房主钥匙与管理令牌。

`/api/state`（前端拿配置的那个接口）**按身份给两种口径**：
普通用户只拿到模型的 `{id, display_name, enabled}`（够渲染参与者名单和「添加模型」候选），
`providers` 一律是空对象；`/admin` 登录后才拿全量（但**仍不含明文 Key** 与**口令哈希**）。

### 用户库：移除昵称 = 直接删除用户（2026-10-15 用户定，两版口径）

用户原话两版（后一版覆盖前一版里"封禁"那半）：

1. 「后台移除昵称后，即从全局删除这个用户，所有聊天室不可见该用户。」
2. 「用户删除功能改成直接删除，删除后即可创建同名用户。」 ← **当前生效**

- 语义 = 「**直接删除**」：`/admin → 用户库` 里点「**移除**」→ 服务端
  `DELETE /api/admin/users/{nickname}`（处理函数 `api_admin_remove_user`）一次做四件事：
  1. `UserStore.remove(nickname)` 从注册表 `data/users.json` **摘掉**（拿回 uid）；
  2. `ConfigStore.remove_member_everywhere(uid)` **遍历所有房间**把 uid 从成员表摘掉、若是房主则清 `owner_uid`；
  3. 把该 uid 的**所有 WebSocket 会话断开**（先推 `removed` 事件、再关连接）；
  4. 刷新受影响房间的成员面板与本轮名单（不清的话，一直不说话的人会卡住整轮）。
- **删完昵称就自由了**（用户明确要的效果）：不再往任何黑名单写东西。同一个昵称**立刻**可以重新登录
  （200），并且拿到的是一个**全新 uid** —— 是「重新登记」，不是「复活旧身份」。
  封禁名单机制（`banned` / `is_banned` / `list_banned` / `unban` / `DELETE /api/admin/banned/{nickname}`）
  **已整体移除**。
- **历史发言保留**：只清人，**不动任何聊天记录** —— 被删的人过去的发言仍在消息池里，仍显示原昵称，
  只是这人不再出现在任何成员名单里。
- **前端**：`app.js` 收到 `removed` 事件 → 清掉本地身份（昵称 / uid / localStorage / `myRooms`）→
  回到出房门槛页，并提示「原来那个昵称现在也可以用了」。
  `/admin` 用户库里每行还标出该用户**在哪些房间**（`userRooms(uid)`），移除前弹确认说明
  「直接删除、昵称立刻可被重新使用、历史发言会保留」。
- ⚠️ **删除 ≠ 清空聊天记录**：这是一条用户明确选定的边界，别顺手把历史一起删。
- ⚠️ **别把封禁加回来**：这是用户二次改口后的口径。真要做「拉黑」得先问，不要自己补。

## 五、几个自查命令

服务**先跑起来**，再开一个窗口：

```
python tools/probe.py --enabled          # 探活模型库里所有已启用的模型
python tools/probe.py --provider zhipu --models glm-4.7-flash,glm-4-flash

python tools/_smoke.py                   # 轻量冒烟（页面控件 / 分权 / 不泄凭据）
node tools/_test_cards.js                # 前端假 DOM 回归（两套页面）
python tools/_test_trash_isolation.py    # 回收站隔离单测（临时目录 + 假回收站，碰不到你的回收站）
python tools/_test_rooms_migration.py    # 房间定义迁移（B 方案）隔离测试

python tools/_check_off_plan.py          # 「关思考」判定速查（不起服务、不耗额度）

                                         # ↑ 预演「还没进模型库」的新模型会不会赌错

python tools/_latency_probe2.py          # 延迟三段计时 + 三组对照（原样 / 关思考 / 关思考+限长，
                                         #   会真打模型、消耗免费额度）；_latency_probe.py 是它的前身

python tools/make_deploy_copy.py         # 生成公网发布副本（发布前跑；旧副本走回收站）
python tools/_diff_local_deploy.py       # 对账：本地 vs 发布副本
python tools/_verify_public_keys.py      # 发布后：校验线上 Key 生效（会真打一次免费模型）
python tools/_verify_public_full.py      # 发布后：完整验收（推荐用这个，跑完自己清掉探针昵称）
```

⚠️ `python tools/_test_trash_isolation.py` 是**唯一**能验到「公网（Linux 沙箱，没有系统回收站）
里删除房间为什么失败」的地方 —— 它在临时目录里把 `recycle.available()` 打成假值，逼出两条分支
（真删 / 交给系统回收站），**全程不碰你本机的回收站**。`selftest.py` 在本机跑，只覆盖 Windows 那条。

`_test_cards.js` 是**纯静态 + 假 DOM**：把 `static/app.js` 与 `static/admin.js` 分别塞进两个
node 沙箱里真跑一遍渲染函数，断言卡片结构、权限门控、请求头编码等。
中文输出会串码，可加 `REPORT_OUT=tools/_cards_report.txt` 让它自己写成 UTF-8 文件再读。

`probe.py` 探活失败时记住排查顺序：**先看模型 ID → 再看 base_url → 最后才怀疑代码**。
这类问题里 90% 是模型 ID 写错、或该模型在厂商控制台没开通。

⚠️ `selftest.py` 会完整走一遍回收站流程，包括「彻底删除」——也就是说
**每次跑自检，会有 1~3 个小文件被放进 Windows 回收站**（自检自己造的房间，约几 KB）。
它会先记录回收站原有内容，只清理属于自检的条目，不碰你原有条目。

自检还会**临时建一个 `provider=mock` 的模型**来跑房间链路，跑完自己删掉 ——
跑完模型库和房间列表都回到跑之前的样子（不依赖模型库里那两条自检模型的开关状态）。

## 七、发布到公网（2026-10-15）

本机自用**不变**（双击 `start.bat`，只听 `127.0.0.1:8765`）。要让别人也能用，走内置的
「发布为应用」——平台会把项目源码上传到沙箱、装依赖、在**一个公网端口**上把服务跑起来。

### 本地和公网是两份东西（别当成同一份）

**代码是同一份，配置和数据完全分开。**

| | 本地（自用） | 公网（发布后的沙箱） |
|---|---|---|
| 目录 | `output/multi-ai-chatroom/` | `output/.deploy/multi-ai-chatroom/` **上传到云沙箱** |
| 前端 / 后端代码 | ✅ 唯一事实来源 | 发布那一刻的**快照**（实测 16 个文件逐字节一致） |
| `config.json` | 含**真实 API Key** | **同样带真实 Key**（2026-10-15 定 B 方案，见下节）；**刻意不含 `rooms`** |
| `data/`（房间定义 / 聊天记录 / 昵称表） | 本机真实数据 | **不上传**（线上自己长），所以**线上房间不会被重发布清掉** |
| `tools/`、`*.md`、`_*.log` | 有 | **不上传** |
| 你改了之后 | 立刻生效 | **不会自动同步** —— 必须重新生成副本 + 重新发布（规则见下节） |

对账脚本：`tools/_diff_local_deploy.py`（跑一次就列出"哪些一致 / 哪些没上传 / 哪些内容不同"）。

⚠️ **开发一律在本地**：发布工具只做「压缩上传 → 沙箱装依赖 → 起服务」，**不提供任何进入沙箱改文件的通道**，
所以公网那份不能当开发环境用 —— 本地才是事实来源。

### 定下来的同步规则（B 方案：Key 随副本上传，2026-10-15 用户定）

用户原话：「把本地的 key 直接填写到公网，后续的开发也自动补上 key。」

所以发布副本**不再脱敏**，`config.json` 原样带上真实 Key。由此定下四条规则：

1. **本地 `config.json` 是唯一事实来源。** 改 Key、改管理口令、加模型、改规则，都在**本地**的 `/admin`
   里改（写进本地 `config.json`），然后 `python tools/make_deploy_copy.py` 重新生成副本 → 重新发布。
   **线上从此不用手填 Key。**
2. ⚠️ **线上直接改的配置会被下次重发布覆盖。** 在公网 `/admin` 里改的口令 / Key / 模型 / 规则 / 角色
   只活在沙箱里，下一次重发布就被本地那份盖回去。
   ✅ **但「房间」不算了** —— 2026-10-15 起房间已经搬出 `config.json`（见下面《哪些算配置、哪些算数据》）。
3. ✅ **线上房间、聊天记录和昵称表都不受影响** —— 它们都在 `data/` 里，而 `data/` 不在上传范围内，
   重发布不动它。（实测佐证：2026-10-15 重发布后，线上原先注册的昵称仍在。）
4. ⚠️ **代价：真实 API Key 现在存在云沙箱里**，与最初"不上传 key"的口径相反 —— 这是用户明确改的口径。
   好消息：`/api/state` 只回 `key_hint` 掩码（如 `sk-ws-…Mz4A`），**别人即使登进 `/admin` 也读不到明文 Key**。

> 之前提过的另外两条路（A 每次手填 / C 把配置改存到 `data/`）**没有采用**，留此备查。

#### 房间为什么搬了家（原「最大的坑」，已修）

用户提问时我核对代码发现：**房间听起来像数据，实际存在 `config.json` 里 = 配置** ——
所以**别人在公网上新建的房间，你下次重新发布会全部消失**（房间名、房间号、参与者、成员表一起没）；
他们的聊天记录文件还躺在云上 `data/rooms/` 里，但**没有任何房间再引用它**，界面上找不回来、也进不去
（`_backfill_rooms()` 只给**已存在**的房间补字段，**不会**从 `data/rooms/*.json` 反向把房间"复活"）。
线上 `/admin` 改过的口令、真人成员表同理会被本地那份盖掉。

**修法（用户选 B 方案，2026-10-15）**：把房间定义整体搬到 **`data/room_index.json`**，
`config.json` 里**刻意不再写 `rooms`**。三级来源、幂等：

1. `data/room_index.json` 有 → 用它（**正常路径**，公网重发布也走这条）；
2. 没有 → 拿 `config.json` 里遗留的 `rooms` 做**一次性迁移**（升级前的老项目）；
3. 连 `config.json` 也没有 → `[]`，随后自动补出**默认讨论室**（全新沙箱不会卡在零房间）。

⚠️ 路径刻意放在 `data/` **根下**、不在 `data/rooms/` 里 —— 后者是「一个房间一个历史文件」，
放进去会和某个 id 恰好叫 `index` 的房间撞名。`reload_if_changed()` **同时盯两个文件**的 mtime。

#### 这次发布的过渡处理（一次性）

线上那份 `config.json` 里还存着房间，而新版服务是「先看 `data/room_index.json`；没有才从 `config.json` 迁」。
所以重新生成的发布副本**会带上 `rooms` 作为「一次性迁移载荷」**（脚本默认行为）：线上首次以新版启动时
把它们搬进线上索引；**线上已有索引之后，载荷被忽略、不会覆盖线上房间**。
线上独有的房间（别人在公网建的）不在本地，用 `--merge-rooms` 并进来（见《发布副本怎么重新生成》）。

**要长期生效的改动，一律在本地改 → 重建副本 → 重新发布。** 线上只当临时改动。

### 为什么不能直接拿项目目录去发

项目目录里有三样东西**不该上公网**：

1. `data/` 是本机的**真实聊天记录 + 昵称注册表**；
2. `tools/` 是本机脚本（自检、探针、一次性补丁）；
3. `*.md`、`_*.log`、`.bat` 是文档与本机运行产物，发布用不上。

（`config.json` 现在**是**要上传的 —— 它带着 Key，见上节。）

所以发布源固定用 **`output/.deploy/multi-ai-chatroom/`** 这份副本，只挑运行必需的文件：
`app/`（去 `__pycache__`）+ `static/` + `run.py` + `requirements.txt` + `config.example.json` + `config.json`，
**一共 17 个文件**；**不带** `data/`、`tools/`、文档。

### 发布时的一个坑：平台自动探测的入口是 `main.py`

本项目入口叫 `run.py`，**必须显式指定启动命令**，否则平台按 `main.py` 找 → 60s 超时
（`can't open file '/workspace/main.py'`）。实测可用的组合：

```
language: python
installCmd: "pip install -r requirements.txt"
startCmd:   "python run.py"
```

### 发布副本怎么重新生成

```
python tools/make_deploy_copy.py              # 默认：Key 一起带上 + 房间作一次性迁移载荷（现在的口径）
python tools/make_deploy_copy.py --no-keys    # 备选：清空 Key（回到"线上手填"的老口径）
python tools/make_deploy_copy.py --no-rooms   # 备选：不带房间载荷（线上若还没索引，只会得到默认讨论室）
python tools/make_deploy_copy.py --merge-rooms online_rooms.json   # 把线上独有的房间并进载荷
```

脚本先清空副本目录（走 Windows 回收站）再重新复制，所以不会有残留；
跑完打印文件清单 + "带 Key / 被清空"的厂商名单 + 迁移载荷里带了哪几个房间。
⚠️ 带上 Key 之后，**这个副本目录和 `config.json` 一样敏感**：别提交 git、别放同步盘。

#### ✅ 推荐流程：先探线上，再带 `--merge-rooms` 重建（2026-10-15 第十一批 起照抄）

```powershell
python tools\_probe_online_rooms.py --out tools\_online_rooms.json   # ① 只读探线上，必须带 --out
python tools\make_deploy_copy.py --merge-rooms tools\_online_rooms.json   # ② 并进线上独有房间
# ③ 用内置「发布为应用」发布 output/.deploy/multi-ai-chatroom/
# ④ python tools\_verify_public_full.py
```

**为什么每次都要走这一遍**：线上房间的长期事实来源是**线上自己的** `data/room_index.json`（`data/` 不上传）。
重发布时副本 `config.json` 里的 `rooms` 只是「一次性迁移载荷」，**线上已有索引时会被忽略** ——
于是**本地没有、线上独有的房间**（别人在公网页面上建的）不并进来就会在重发布后**消失**。

- ⚠️ **`_probe_online_rooms.py` 必须带 `--out`**：不带的话 `tools/_online_rooms.json` 还是**上一次的快照**，
  `--merge-rooms` 会把一个**线上早已不存在的房间 id** 并进载荷（不影响线上，但等于白做，还会误判）。
- `--merge-rooms` **是安全操作**：按 id 去重、只补本地没有的、同 id 以本地为准；
  线上已有索引时它是**无害 no-op**，线上没有索引时才起保护作用。**永远带上不会错。**
- 取线上房间也可以手动：`POST /api/admin/login`（口令）拿令牌 → `GET /api/state` 带 `X-Admin-Token`，
  把返回里 `config.rooms` 存成 JSON 文件；或直接登线上 `/admin` 从浏览器网络面板里取。
- ⚠️ **`--merge-rooms` 能保住什么、保不住什么（2026-10-15 实测核实）**：
  `code`（房间号）与 `owner_key`（房主钥匙）是刻意不外发的凭据 —— **普通口径与管理员口径的
  `/api/state` 都取不到**（实测恒为 `None` / 空串）。所以并进来的房间**只有定义**
  （名称 / 参与者 / 成员表 / `owner_uid` / `open` / `no_owner` / `debate`），
  **房间号与房主钥匙并不过来**：线上若真的消费了这份载荷，该房间会被重新分配房间号、原房主失去旧钥匙。
  好在**线上已有 `data/room_index.json` 时载荷是被忽略的 no-op**（本批就是这种情况），线上一切原样；
  只有在**线上还没有索引**（第一次上 B 方案）时才会真的消费载荷 —— 那一次要接受"线上独有房间的
  房间号/房主钥匙会变"这个代价（或先用 0 消息的空房间、让房主重新认领）。

### 已知限制 / 没验证的部分

- 沙箱只给**一个 HTTP 端口**，没有数据库；本项目的持久化是 **JSON 文件**（`config.json` + `data/`），
  这属于官方支持的形态。
- ✅ **WebSocket 已经实测穿过平台的 HTTPS 反代**（2026-10-15）：`wss://<host>/ws` 连接成功 → 发 `join` →
  收到 `hello / joined / members / round_state`，`joined` 回 `ownerless: true`，上行也通。
  复现脚本 `tools/_probe_public.py`（日志 `tools/_public_log.txt`）。
- 免密码身份一旦上公网就是**真的任何人可冒名**（本机用无所谓，公开用要自行权衡）。
- 发布副本里的 `config.json` 是**快照**，而且现在**带真实 Key**：本地改了模型库 / Key / 口令，
  必须重新生成副本 + 重新发布才会同步；反过来，线上直接改的配置下次重发布会被覆盖。

## 八、已知坑（都是实测踩到的）

1. **免费模型会限流**：`glm-4.7-flash` 实测返回 429（`1302 账户已达到速率限制` / `1305 模型访问量过大`）。
   调用层已做指数退避重试，且只在**还没吐出内容**时重试（吐了一半再重试会导致内容重复）。
   主用模型因此换成了实测稳定的 `glm-4-flash`。
2. **推理模型的正文可能完全不在 `content` 里**：`glm-4.7-flash` / `glm-4.5-flash` / `glm-5.3-flash`
   都会把正文写进 `reasoning_content`。`glm-5.3-flash` 在 `max_tokens=256` 时正文 0 字、推理 1174 字。
   调用层同时解析三种字段名，前端把推理过程单独折叠显示，不混进发言正文。
3. **`/models` 列表不完整，只当辅助**：智谱的 `/models` 返回 11 个模型，但**不含 `glm-4-flash` /
   `glm-4.7-flash` 这些 `-flash` 老版本**（它们实际能调）。所以页面的「拉取列表」只是辅助，
   真要确定模型 ID，以厂商控制台/文档为准。火山方舟的列表更夸张：135 条里 100 条是
   `Shutdown`/`Retiring`，拉取时会自动过滤掉并提示过滤了多少条。
4. **中文房间名不能直接进 HTTP 头**：导出时 `Content-Disposition` 里的中文会导致 latin-1 编码失败
   → 500。已改为 ASCII 文件名 + `filename*=UTF-8''` 双写。这个 bug 是自检脚本抓出来的。
5. **成本护栏按全局计数，不按房间**：多房间并行会共用同一批免费额度。
   计数上限在 `config.json` 的 `cost_guard.max_total_calls`（当前 200）。
6. **上下文会随轮次膨胀**：超过约 30000 字符时自动只保留最早的 2 条 + 最近的 10 条，
   中间插入省略提示。「定向回应」和「点名发言」会额外加速膨胀。
   （这个阈值 2026-10-13 从 14000 抬到 30000 —— 因为字数上限取消了，发言会变长。）
7. **规则里刻意不推对抗**：`shared_prompt` 已删掉「必须提出至少一条与其他发言者不同的观点」，
   并在 2026-10-13 换成「不要为了附和别人而改变判断，也不要为了反对而反对」。
   想调讨论风格，去 `/admin` →「规则」改（2026-10-14 起规则**也只能在 /admin 改**，首页左栏是只读的），
   或直接改 `config.json` 的 `shared_prompt` 再点「重载」。
   另外**模型不再自报发言类型**，消息头也没有【陈述】【质疑】彩标——那是 2026-10-13 主动取消的。
8. **控制台显示名 ≠ API 模型 ID**（2026-10-12 实测）：方舟控制台里的「Doubao-Seed-2.1-lite」在 API 层是
   `doubao-seed-2-1-lite-260915`（小写 + 日期版本号）。直接填显示名一律 404。
   `/models` 能列出 ID 但**大部分未开通**，报错分两种：`does not exist`（ID 错/未开通）与
   `has not activated the model ... activate in Ark Console`（明确让你去控制台开通）。
9. **腾讯混元已迁到 TokenHub，两套端点不通用**：TokenHub 控制台发的 Key 必须打
   `https://tokenhub.tencentmaas.com/v1`；打旧域名 `api.hunyuan.cloud.tencent.com` **必 401**。
   换对端点后模型未开启会报 `402 / 401006`。⚠️ 控制台**不要点「一键开启」**——
   那会把 117 个模型全开成按量计费，免费额度耗尽会自动扣费。
10. **别用并行编辑改同一个文件**（本机工具行为，2026-10-13 踩到，**2026-10-14 又踩两次**）：
    同一条消息里对同一个文件发多个编辑，会出现"工具报告成功、但改动没落盘"的情况。
    10-13 因此漏掉 `TRASH_DIR` 导入和 `/api/state` 的 `trash` 字段；10-14 又漏掉两处
    `from urllib.parse import ...` 的导入（被同文件另一条编辑整段覆盖），症状分别是
    `NameError: name 'quote' is not defined` 和「`unquote` 没导入却被 `except` 吞掉、
    函数静默返回 `{}`」——后者最坑，因为它**不报错**，只表现为权限判断一律失败。
    **同一文件必须一条一条改；改完必须回读，或跑一次能覆盖该路径的自检。**
11. **开着的旧标签页不会自己更新**（2026-10-13 实测）：用户从昨天开到今天的页面，代码更新后
    仍跑旧 DOM，曾出现「厂商标题插在模型列表中间」这种任何版本都渲染不出的乱序。
    已加自愈机制（页面 15 秒对一次构建号，过期自动刷新），但**升级那一刻仍需手动关掉旧标签页重开一次**。
12. **卡片副标题别再用 `word-break: break-all`**（2026-10-13）：长英文会被从中间劈开
    （"TokenHub" → "Token Hub"），且长短不一的副标题把卡片撑成 1~3 行高、按钮行错位。
    现在统一 `card-sub one`（单行省略）/ `card-sub two`（两行截断 + min-height），改样式时别绕回去。
13. **发言类型机制是一整套，删干净才不会反噬**（2026-10-13）：
    「标签」不只是提示词里那一句 —— 它串着 `providers.SPEECH_TYPES` / `_TAG_RE` / `split_speech_tag`、
    `orchestrator._infer_type` 兜底、消息的 `speech_type` 字段、前端 `.chip` 四条配色、
    导出与转录里的类型标记。**当时如果只删提示词那一句、留着兜底逻辑，所有发言会一律被记成「质疑」**，
    比不做更糟。所以这五处是一起删的。
14. **角色只能从预置库里选，不要再给自由文本入口**（2026-10-13）：`rooms[].participants[].role_override`
    存的是 `role_presets` 里的 **id**（如 `skeptic`）。填自由文本不会报错，但会解析成"无角色"，
    且界面上没有任何提示——排查时先看 `config.json` 里这个字段是不是合法 id。
    加角色请改 `role_presets.items`（id / name / group / prompt 四个字段都要有）。
15. **角色只设在房间参与者上，模型库不存角色**（2026-10-13 用户定稿）：`models[]` 没有 `default_role`
    字段（配置与后端 `resolve()` 都不认它），角色唯一入口是房间参与者的「角色」下拉；
    不设就是无角色，system 提示词里没有「你在这场讨论里的角色」这一行。别再把角色加回模型编辑弹窗。
16. **本机自检模型不能进真实房间，也不该出现在「厂商 / API Key」里**（2026-10-13 用户要求）：
    `provider=mock` 的两条自检模型必须保持 `enabled: false`。
    （2026-10-14 起「新建房间自动带上全部启用模型」这条已经取消，所以不再有"一启用就污染每个新房间"的
    连带效应；但它们仍然只是给自检用的假数据，别手动加进真实房间。）
    `providers.mock` 已从配置里删掉；`resolve()` 对缺失厂商是容错的（`providers().get(pid) or {}`），
    所以删厂商不影响这两条模型继续可用，但前端模型卡片的厂商名要兜底，否则副标题会显示成裸 id「mock」。
    自检脚本因此改成自己临时建一个模型跑房间链路，不再依赖这两条的开关状态。
17. **拉取模型列表失败，别甩锅给厂商**（2026-10-13 用户要求核实后改）：
    实测**智谱 / 火山方舟（豆包）/ 百炼（千问）/ TokenHub（混元）都有 `GET /models`**，
    GitHub Models 的目录在 `/catalog/models`（不在推理 base `/inference` 下，返回裸数组）。
    所以原来的提示「该厂商可能不提供 /models 接口，请手填模型 ID」在多数失败场景下**是错的**：
    没配 Key（401）、base_url 指错层级（返回 HTML）、路径不对，都会被说成"厂商不支持"。
    现在后端把失败分成 `no_base_url` / `no_key` / `auth` / `unsupported` / `not_json` / `network` / `http`
    七类，前端按类说人话，**只有 `unsupported` 才提示手填**。
    - 配置里 `supports_model_list` 是**事实声明**，写 `false` = "已核实没有该接口"（界面连请求都不发），
      所以不能凭感觉填；配套 `model_list_verified` / `model_list_note` 记录核实状态与依据。
    - 列表接口不在 `/models` 的厂商，用 `models_url`（整条 URL）或 `models_path` 覆盖，
      特殊请求头用 `models_headers`。
    - 排查脚本：`tools/_probe_models.py`（只发 GET，不消耗 token 额度），结论表见 `PROBE.md` 第二节。
18. **`X-Owner-Keys` 头值必须纯 ASCII**（2026-10-14，用户报「房间复制、删除、创建功能有问题了」的真因）：
    房间 id 是**房间名** slug 来的，所以**中文房间名会得到含中文的 id**（如 `测试-9b0986`）。
    而 `fetch` 的请求头值只接受 ≤0xFF 的字符（ByteString）——
    `api()` 里 `JSON.stringify(myKeys)` 直接塞进头里，一旦 `myKeys` 出现中文 key，
    **每一次 REST 调用都在发请求之前抛 `TypeError: Cannot convert argument to a ByteString...`**。
    症状极具误导性：不是"某个功能坏了"，而是**建/复制/删/改名全挂且毫无提示**
    （当时这些处理函数没有 try/catch，Promise 静默 reject），而且钥匙存在 localStorage 里，
    **刷新也修不好**；只有换了浏览器或清了站点数据才「恢复」。
    - 修法：前端 `encodeURIComponent(JSON.stringify(myKeys))`，服务端 `_owner_keys()` 先
      `unquote` 再 `json.loads`（编码过的值必以 `%7B` 开头、未编码的以 `{` 开头，两种都认）。
    - 同类前科：导出时的 `Content-Disposition`（见已知坑 4）—— 同一个"中文不许直接进 HTTP 头"的坑。
    - 回归防线：`tools/_test_cards.js` 用 node 的真 `Headers` 做与浏览器同款的 ByteString 校验
      （`new Headers({...})` 会抛同样的 TypeError），再加一条"未捕获 Promise 必须有兜底提示"的行为断言；
      `tools/selftest.py` 的 `keys_header()` 改成复刻浏览器（`quote(json.dumps(..., ensure_ascii=False))`）——
      ⚠️ 以前用 `json.dumps` 默认的 `ensure_ascii=True` 会把中文转义成 `\uXXXX`（纯 ASCII），
      **侥幸躲过了这个 bug，所以自检一直测不出来**。测试替身"太好说话"会掩盖真实故障。
19. **管理口令的令牌是"无状态派生值"，所以改口令 = 踢下线**（2026-10-14）：
    `admin_token = sha256(salt | password_hash | 版本串)`。好处是**服务重启后 /admin 不用重新登录**；
    代价是**口令一改，哈希变 → 令牌变 → 所有已登录的 /admin 页面立刻 401**。
    所以 `admin.js` 在 `savePassword()` 成功后**必须把新令牌存回 localStorage**，
    否则改完口令当前页面下一个请求就被判未登录。改口令请只在 `/admin` 页面里改 ——
    手改 `config.json` 里的 `password_hash` 会被 `_backfill_admin()` 的幂等判断挡住（它只看有没有哈希）。
20. **给前端做"搬迁"时，测试替身会全体过期**（2026-10-14，把模型库搬到 `/admin` 时踩到）：
    `tools/_test_cards.js` 原来直接调 `sandbox.renderModels()` —— 函数搬去 `admin.js` 后测试**当场崩**
    （`TypeError: sandbox.renderModels is not a function`）。而且假 DOM 里 `renderModels` 依赖的
    `modelList` / `providerList` 等 id 也已经不在 `index.html` 里了。
    处理方式：把测试拆成**两个沙箱**（`app.js`+`index.html` 一套、`admin.js`+`admin.html` 一套），
    并给每个沙箱**按它引用的 id 预置桩元素**（而不是维护一份手写 id 清单 —— 手写清单迟早漏）。
    另外加一条断言：**js 里 `$('#xxx')` 引用的每个 id 都要在对应 html 里有定义**，
    这样"删了 html 忘了删 js"会立刻红，而不是等到运行时才炸。
21. **「房间」看着像数据，其实以前是配置 —— 现在搬进 `data/` 了**（2026-10-15）：
    房间原来存在 `config.json → rooms[]`，而发布时会用本地那份**整体覆盖**线上配置，
    于是**线上新建的房间会被下一次重发布清空**（历史文件还在 `data/rooms/`，但没有房间引用它）。
    现在房间定义的事实来源是 **`data/room_index.json`**（`data/` 不上传），`config.json` 里**刻意不写 `rooms`**。
    - ⚠️ **别把 `rooms` 加回 `config.json`**，也别让它进发布副本的常规配置 ——
      副本里那份是给线上做**一次性迁移**用的载荷，线上有索引后就被忽略。
    - ⚠️ 迁移顺序有讲究：服务启动时是「**先看索引，没有才读 `config.json` 的 `rooms`**」。
      如果哪天你手贱把 `data/room_index.json` 删了，服务会拿 `config.json` 里**残留**的 rooms 或直接
      播种默认讨论室 —— 线上房间就找不回来了。要备份就备份整个 `data/`。
    - ⚠️ **改数据模型会打红老断言**：`config.json` 里不再有 `rooms` 后，
      `selftest.py` / `_test_cards.js` 里所有「读配置文件取房间」的断言都要改读 `data/room_index.json`
      （已加 `read_rooms_from_disk()` 与 `cfg.rooms` 兜底）；**红的是断言不是代码**。
